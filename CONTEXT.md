# Context

## Purpose

A personal tool that scrapes daily newspapers' web editions and packages each one into its own Kindle-ready `.epub`, organized by section (front page, sports, editorial, etc.), one article per page. Currently covers [Jugantor](https://www.jugantor.com/todays-paper), [Prothom Alo](https://www.prothomalo.com), [Dhaka Tribune](https://www.dhakatribune.com), and [The Daily Star](https://www.thedailystar.net/todays-news); each is a separate epub, built by a separate source module, so more can be added the same way.

**"Section" is a per-source abstraction, not a fixed real-world concept**: `discover_sections()` returns whatever division of the day's news that source's own site organizes itself by. For Jugantor that's its literal print-edition categories (`tp-*` slugs like front page/sports/editorial). Prothom Alo has no equivalent print-edition text site, so its "sections" are its regular web nav categories (bangladesh, sports, world, etc.) instead. Dhaka Tribune's nav is a full mega-menu mixing real verticals with subcategories and vague catch-alls, so its section list is a curated allowlist confirmed against the live nav rather than a generic filter rule. The Daily Star goes a step further still: it has no per-category page at all, so its "sections" are derived from each article's own URL rather than from any nav or listing structure — four different ways of arriving at the same contract shape.

**Cover presentation (logo prep, accent color, date format) is also per-source, not just per-language**: `format_date()` was added when Dhaka Tribune (English) joined two Bengali papers — rendering a Bengali-formatted date under an English masthead read as a mismatch, so each source module now owns its own date formatter (`bengali_date.format_bengali_date` or `english_date.format_english_date`, both shared, language-agnostic-to-any-specific-paper formatting utilities) rather than `main.py` hardcoding one language for every source.

## Why this exists

The newspaper publishes its daily edition as a set of article-listing pages rather than a downloadable format, so reading it comfortably on an e-ink Kindle (rather than a phone browser) requires converting it. This is a from-scratch personal project — not built on an existing codebase.

## Key decisions and why

- **Python, not Node.js** — good scraping/imaging/epub library support (`requests`+`BeautifulSoup`, `Pillow`, `ebooklib`).
- **Scrape HTML directly, no API** — the site is server-rendered with no anti-bot wall encountered during research; no API was found or needed. Article metadata comes from clean `<script type="application/ld+json">` blocks embedded in each article page, which is more reliable than parsing visible HTML for headline/author/date.
- **All sections, with images, today's date only** — chosen to match "the full daily edition" reading experience over a trimmed-down digest. Historical/back-issue support (the site supports a `?date=` query param) and a curated-subset mode were both explicitly deferred rather than built speculatively. "Today's date only" is enforced structurally for Jugantor and Dhaka Tribune (their listing pages are inherently a single day's/single page's worth of content), but had to be added explicitly for Prothom Alo — see the Prothom Alo quirks entry below.
- **Embed a Bengali font in the epub** — Kindle devices have no built-in Bengali-capable font, so without embedding one, all Bengali text would render as blank boxes on-device. Noto Sans Bengali (SIL OFL) was chosen as a freely-redistributable open font.
- **Each newspaper is a fully separate source module, sharing only genuinely paper-agnostic code** — `jugantor_epub/sources/{jugantor,prothomalo,dhakatribune,dailystar}.py` each own their own URLs, section lists, and HTML/JSON parsing logic independently. What's shared is deliberately narrow and general-purpose, never a specific paper's DOM/JSON shape: `text_utils.py` (NFC Unicode normalization), `ld_json.py` (selecting a `<script type="application/ld+json">` block by its schema.org `@type`, since several sites bury the useful block behind an `Organization`/`BreadcrumbList` block, or - Daily Star - bundle every type into one block via a schema.org `@graph` array), `bengali_date.py`/`english_date.py` (date formatting), and `jugantor_epub/cover.py` (cover rendering, parameterized per source with its own logo URL/path, accent color, date formatter, and optional logo-cleanup hook). Each source module still builds its own independent `.epub`.
- **Daily automation via scheduled GitHub Actions, not local cron/launchd** — `.github/workflows/daily-kindle.yml` runs `main.py` on a daily schedule (plus manual `workflow_dispatch`), so the pipeline runs even when the personal machine is off. Local runs (`.venv/bin/python main.py`) still work unchanged and just build into `output/` without emailing anything.
- **One Kindle email per built source, not one combined email (revised 2026-08-18)** — `jugantor_epub/email_sender.py`'s `send_to_kindle(epub_entries, edition_date)` is called once from `main.py` after *all* sources have finished building, but sends a separate message per `(source_name, epub_path)` entry rather than attaching every epub to one message. The original design (see the 2026-08-11 design doc) combined everything into a single daily email to avoid spamming the Kindle inbox; that broke once Prothom Alo's larger article count pushed its epub past ~24MB, tipping the *combined* message over Gmail's 25MB send limit and silently losing Jugantor's and Dhaka Tribune's editions too, even though those were well within the limit on their own. Per-source sending means one oversized epub only costs its own delivery — `send_to_kindle()` skips (with a logged warning) any entry too large for Gmail's limit after base64 encoding, and only raises if literally nothing could be sent. Sending is gated behind the `config.SEND_TO_KINDLE` env-driven switch (defaults off; the GitHub Actions workflow sets `SEND_TO_KINDLE=true`), and `main.py` exits non-zero if every source fails to build or every send attempt fails, so a scheduled run failure is visible in the Actions tab.
- **OPDS catalog as a second, independent delivery path (GitHub Pages)** — added alongside Kindle email so the user's Boox e-ink device (via KOReader/Moon+ Reader, which support OPDS; stock Kindle firmware does not) can browse and pull editions directly. Organized by newspaper, not by date: a root navigation feed lists one entry per configured source, each linking to that source's own feed holding its last 7 *successfully built* editions by count (not a calendar window). No auth — an explicit, informed choice for simplicity over content protection. See `docs/superpowers/specs/2026-08-13-opds-catalog-design.md` for the full design rationale.
- **Local git identity: `Mehedi Hasan <mehedipy@gmail.com>`, not the work email** — this repo pushes to a personal GitHub account (`git@personal.github.com:mehedibangladeshi/DailyNewspaperPublish.git`, matching the existing `personal.github.com` SSH host alias used by other personal repos like `ai-skills`), so the commit identity is scoped to match, distinct from the global work-email default used elsewhere on this machine.

## Architecture summary

See `CLAUDE.md` for the details future coding sessions need (commands, the parse/fetch split, error-isolation pattern, Unicode normalization gotcha, JSON-LD parsing quirks, font-embedding bug history, cover generation). In short: `main.py` orchestrates a discover → scrape → build pipeline over source modules listed in `jugantor_epub/config.SOURCES`; each source module under `jugantor_epub/sources/` implements a small contract (section/article scraping plus a masthead-logo URL for the cover) so more newspapers can be added later without touching `main.py`.

## Known site quirks worth remembering

Found during initial scraping research and while fixing a code review pass — not obvious from reading the code alone:

### Jugantor

- Some article pages embed a **raw literal newline inside a JSON string value** in their `ld+json` block (e.g. a multi-line headline), which breaks strict JSON parsing. Handled via `json.loads(..., strict=False)`.
- `ld+json` fields (headline, author, image) can be **present but explicitly `null`**, not merely absent — `dict.get(key, default)` doesn't catch that case; code must use `dict.get(key) or default`.
- The site **mixes NFC/NFD Unicode normalization** for Bengali nukta characters (e.g. "ড়") across different fields on the same page — text is normalized to NFC on extraction for consistent comparison/rendering.
- At least one observed image URL from the site's own data contained an unencoded `'` producing a broken CDN path — this fails gracefully (image skipped, article still included) rather than being treated as a code bug.

### Prothom Alo

- Has **no print-edition text equivalent** to Jugantor's `/todays-paper` — its `epaper.prothomalo.com` is a scanned-image flipbook, not usable for text extraction. Its regular web category pages (bangladesh, sports, world, etc.) are scraped instead, discovered from the homepage's `#navbar` nav.
- Category pages are **Quintype-CMS-powered with no scrapeable DOM listing cards** — per-article listing data lives entirely in a `<script type="application/json" id="static-page">` blob, as a deeply nested, recursive `collection → items → story` tree. The same story routinely appears more than once (multiple listing widgets reuse it), so listing extraction must dedupe by story `url`.
- Unlike Jugantor, the **first `ld+json` block on an article page is a `BreadcrumbList`**, not the article metadata — the block with `"@type": "NewsArticle"` must be located explicitly among the 2-3 ld+json blocks present.
- `ld+json`'s `author` field is a **list of Person dicts** (`[{"name": ...}]`), not a single dict/string like Jugantor's.
- Subscriber-only (premium) articles are detected via `ld+json`'s `isAccessibleForFree: false` and skipped (raised from `fetch_article`, caught by `main.py`'s existing per-article error isolation) rather than included as truncated teasers.
- **Unlike Jugantor's print-edition pages, a category page has no natural "today only" bound** — it's the site's regular web nav, which lists a rolling collection of recent stories regardless of date (30–74+ per section observed, vs. Jugantor's fixed ~10). This is what made a single day's combined epub balloon past Gmail's send limit once Prothom Alo joined (2026-08-18). Fixed at the listing-parse level: each story in the `static-page` JSON already carries its own `published-at` epoch-ms timestamp (sitting next to `headline`/`url`), so `parse_articles()` converts it to an Asia/Dhaka calendar date and drops anything not matching the run's `edition_date` — before any article-detail fetch or image download happens, not as an epub-build-time trim. An item missing/with an unparseable `published-at` is kept (fail open, logged once) rather than dropped, since this is a newly-relied-on field with no track record yet of being reliably present across every section's JSON shape.
- **`video` and `chakri` (jobs/classifieds) are excluded from `FALLBACK_SECTIONS` and live-discovered sections alike** — not a date problem, a content-fit one. Kindle can't play video (a video-story page's body is a player + caption, not prose), and job listings aren't news narrative the way the rest of the paper is. Same "curated allowlist over generic filter" spirit as Dhaka Tribune's `CORE_SECTION_SLUGS`, just expressed as a denylist since only two of Prothom Alo's ~10 nav categories needed excluding.

### Dhaka Tribune

- The **only English-language source** so far — its cover uses `english_date.format_english_date()` instead of the Bengali formatter, and it needed no `prepare_logo_image` cleanup at all: `logo-en.png` is already a tightly-cropped, transparent-background wordmark (unlike Prothom Alo's banner asset).
- Has **no usable print-edition text site** — `epaper.dhakatribune.com` is a JS-rendered scanned-image viewer (a React app pulling page images from a crop/media API), same dead end as Prothom Alo's e-paper. Its regular web category pages are scraped instead.
- The nav is a **full mega-menu**, not a flat category list — real editorial verticals are mixed with subcategories, an aggregate "News"/`latest-news` page, and vague catch-alls ("More", "Magazine"). `CORE_SECTION_SLUGS` is a curated allowlist rather than a generic filter, confirmed against the live nav. Notably, **"Bangladesh" (the flagship section) sits nested one level under "News"**, not top-level itself — `parse_sections()` scans the whole nav tree (not just top-level `<li>`s) so it's still found and promoted into the section list.
- Listing pages **are** scrapeable DOM cards (`div.each`, with a `.summery` class — the site's own spelling, not a typo introduced here) — closer to Jugantor's approach than Prothom Alo's embedded-JSON one. Thumbnails are lazy-loaded via a JS-resolved `data-ari` blob (a partial media path missing the CDN's size/upload segments) rather than a plain `<img src>`, so listing thumbnails are left `None` — `fetch_article`'s `ld+json` image is reliable and is what `main.py` prefers anyway.
- Like Prothom Alo, the **first `ld+json` block is not the useful one** (an `Organization` block comes first, `NewsArticle` is third) — selected via the shared `ld_json.select_by_type()` helper.
- No paywall/premium signal found on this site (only a push-notification subscribe bell, not an article paywall), so `fetch_article` doesn't special-case anything there.
- **Known, accepted limitation: fails on GitHub Actions' hosted runners (2026-08-18)** — Cloudflare serves a Managed Challenge (`cf-mitigated: challenge`, "Just a moment..." Turnstile page, HTTP 403) to GitHub Actions' Azure-hosted egress IPs specifically. Confirmed by diagnostic probe: the identical `requests` call returns `200` from a residential IP and `403`+challenge from a GH Actions runner; a real headless Chromium (Playwright) hitting the same URL from the same runner also stayed stuck on the challenge page, so it's not a fixable header/fingerprint issue — Cloudflare is scoring the datacenter IP and/or detecting the automation itself. Real fixes (residential proxy, self-hosted runner, stealth-patched browser automation) were all judged not worth the added cost/maintenance for this source. `main.py`'s per-source `try/except` (`build_source_edition` raising when zero articles are scraped) and `opds_publish.py`'s per-source `try/except` already isolate this failure — Jugantor and Prothom Alo still build, send, and publish normally on days Dhaka Tribune 403s. No code changes were made; this entry exists so a future 403 report isn't re-investigated as a new bug.

### The Daily Star

- The **only source with no per-category listing page at all** — `/todays-news` is a single Drupal "views" page that already lists every story published that day (confirmed: every dated card on the page reads today's date, and there's no pager/infinite-scroll markers, so it's a bounded single page, not a rolling feed). `discover_sections()`/`list_articles()` therefore both derive from this one page rather than each fetching their own category URL - "section" here is the first path segment of each article's own URL (`/business/economy/news/...` → `business`), not a real nav category or CMS field.
- Because every section's data lives on one URL, a module-level cache (`_listing_cache`) holds the parsed `{slug: [articles]}` dict for the run so `discover_sections()` and each subsequent `list_articles()` call share a single fetch+parse instead of re-requesting `/todays-news` once per section.
- Listing cards are DOM elements (`.views-row`, with a `.card-title` heading whose level varies - `h3` in most widgets, `h5` in a few - so selection is by class, not tag), closer to Jugantor's/Dhaka Tribune's approach than Prothom Alo's embedded-JSON one. The same story can appear in more than one listing widget, so extraction dedupes by URL, same as Prothom Alo/Dhaka Tribune.
- `star-multimedia` is excluded (`EXCLUDED_SECTION_SLUGS`) - it's a video hub; its article pages carry an embedded player and an essentially empty text body, same "not usable for a text reading digest" reasoning as Prothom Alo's excluded `video` section.
- The site's ld+json bundles **every entity for the page into one block via a schema.org `@graph` array** rather than emitting separate `<script>` blocks per type - `ld_json.select_by_type()` was extended (generically, not Daily-Star-specifically) to also look inside `@graph`, since that's a standard schema.org shape any future source could also use.
- `ld+json`'s `author.name` can be a **list of plain strings** (`["AFP", "Paris"]` - a wire-service credit + dateline), not a list of Person dicts (Prothom Alo) or a single dict/string (Jugantor/Dhaka Tribune). Joined with `", "` when a list.
- **Neither `datePublished` nor `image` are present in the ld+json at all** - both fields have to come from elsewhere: `date_published` from a DOM span (`span.text-gray-600.font-medium`, which shows either an absolute date or a relative one like `"11 HOUR(s)"` depending on recency), `image_url` from the page's `<meta property="og:image">` tag (not `og:image:secure_url`, which points at a dead `images.thedailystar.net` subdomain - see below).
- No paywall/premium signal found, so `fetch_article` doesn't special-case anything there.
- **The live masthead logo has no usable network asset at all** - the real logo is SVG-only (`themes/custom/swallow/logo.svg`), which `Pillow` can't decode; the site's own `og:image:secure_url` (its usual go-to for a raster logo elsewhere in this codebase) points at `images.thedailystar.net`, a subdomain that doesn't resolve in DNS at all (not a transient failure - confirmed dead); and the favicon is only 16×16. Per the user's explicit choice, the SVG was rendered to PNG **once**, offline (`cairosvg`, not a runtime dependency - used only to produce the committed asset) and both the source SVG and the rendered PNG are committed under `jugantor_epub/assets/`. `get_cover_logo_url()` returns the local PNG's path rather than a URL - this needed a small, generically-useful change to the shared `cover._fetch_logo_image()`: a non-`http(s)` string is now read from disk instead of fetched over the network, so any future source in the same situation can reuse the same mechanism.
- No distinct brand accent color exists (the wordmark is flat monochrome navy, no fill color baked into the SVG) - `COVER_ACCENT_COLOR` uses `#040D33`, the site's own recurring UI navy (used ~40 times across the homepage), rather than inventing a color that isn't really theirs.
