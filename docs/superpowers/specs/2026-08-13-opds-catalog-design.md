# OPDS Catalog — Design

## Context

`main.py` already builds a daily `.epub` per configured source (`config.SOURCES`) and, when `config.SEND_TO_KINDLE` is set, emails all of them to a Kindle address in one combined message (see `2026-08-11-daily-kindle-automation-design.md`). Kindle's stock firmware has no OPDS client, so email delivery stays as the Kindle path unchanged by this design.

The user also reads on a Boox-style e-ink Android device, whose reader apps (KOReader, Moon+ Reader, etc.) can browse and pull books directly from an OPDS catalog — an Atom-based feed format for listing and downloading publications. This design adds that as a second, independent delivery path. `config.SOURCES` currently holds one newspaper (`jugantor`) but is about to grow to 5–7; the catalog structure is designed for that scale, not just today's single source.

A throwaway prototype (`prototypes/opds_catalog/{logic.py,tui.py,NOTES.md}`) validated the core retention mechanic — pure functions driving a small TUI — before this design was finalized. It will be deleted once this feature lands; its pure functions are the starting point for the real `opds_catalog.py`, not something to import from.

## Decisions already settled (via direct Q&A, not re-litigated here)

- **Hosting:** static files, no long-running server — regenerated by the same GitHub Actions run that already builds the epubs.
- **Where:** GitHub Pages via a dedicated `gh-pages` branch on `mehedibangladeshi/DailyNewspaperPublish` (public repo, so Pages is free). Served at `https://mehedibangladeshi.github.io/DailyNewspaperPublish/`.
- **Exposure:** public, no auth. The user's explicit choice after being shown the tradeoff (scraped content becomes openly downloadable to anyone with the URL) — accepted for simplicity.
- **State model:** no separate state file. The `gh-pages` branch's own directory listing (dated epub filenames already following `epub_builder.py`'s existing `{slug}-{date}.epub` convention) is the source of truth each run — nothing to keep in sync, nothing that can drift.

## Decision: catalog structure

**Two-level, organized by newspaper — not by date.** (An earlier date-wise structure — one nav entry per calendar day, with that day's newspapers grouped underneath — was explored and explicitly rejected in favor of this.)

- **Root navigation feed** (`catalog.xml`) — one entry per entry in `config.SOURCES`, always, even a source with zero currently-active editions (keeps the newspaper list stable rather than newspapers flickering in and out of the nav on a bad day). Each entry links to that source's own feed.
- **Per-source acquisition feed** (`{slug}/feed.xml`) — that newspaper's editions, newest first, with real acquisition links to the `.epub` files.

## Decision: retention is count-based, not calendar-based

**Each newspaper holds its last 7 successfully-built editions — a count, not a 7-day calendar window.** These agree when a source builds every day, but diverge the moment one skips a day (which `main.py`'s existing per-source try/except already permits):

- A source that's been failing shows old-but-fewer-than-7 editions — nothing is evicted on a day with no successful build.
- A source resuming after a long gap still fills back up to 7 over its next 7 successful builds, whatever calendar span that covers.
- Eviction only happens when an *8th* successful edition lands: the oldest of the previous 7 drops.

This was a deliberate reversal of the calendar-window approach used in the earlier per-source design pass and in the prototype — the user's own phrasing ("last seven editions") was taken literally.

## Storage layout on `gh-pages`

```
gh-pages/
├── catalog.xml                  # root navigation feed
├── jugantor/
│   ├── feed.xml                 # acquisition feed, ≤7 entries
│   ├── jugantor-2026-08-13.epub
│   ├── jugantor-2026-08-12.epub
│   └── ...                      # up to 7 files
├── prothomalo/
│   ├── feed.xml
│   └── ...
└── ...                          # one folder per config.SOURCES entry
```

Filenames inside each `{slug}/` folder are copied byte-for-byte from `output/{slug}-{date}.epub` — no renaming, even though the slug is redundant with the folder name. Zero changes to `epub_builder.py`'s existing naming.

## Decision: entry title format

Each edition entry inside a per-source feed is titled with the full English weekday + day + abbreviated month + year, **not zero-padded**: `Thursday, 3 Aug, 2026` (not `Thursday, 03 Aug, 2026`). This is unrelated to `jugantor_epub/bengali_date.py`, which formats Bengali-script dates for the epub cover and has no weekday — a new small formatter is needed, living in `opds_catalog.py`.

## Components

### 1. `jugantor_epub/opds_catalog.py` (new, pure — no I/O)

Follows the parse/pure-function split already used in `sources/jugantor.py`:

- `parse_edition_filename(filename) -> (slug, date) | None` — parses `{slug}-{date}.epub`.
- `keep_latest_n(filenames, n) -> (kept, evicted)` — sorts by embedded date descending, splits at `n`. This is the count-based retention rule in one function.
- `format_entry_title(edition_date) -> str` — `"Thursday, 3 Aug, 2026"`, no zero-padding.
- `render_source_feed_xml(slug, source_name, kept_filenames, base_url) -> str` — the per-source acquisition feed.
- `render_root_feed_xml(sources: [(slug, source_name)], base_url) -> str` — the root navigation feed, one entry per configured source regardless of whether it currently has any active editions.

### 2. `jugantor_epub/opds_publish.py` (new, I/O wrapper — mirrors `email_sender.py`'s role)

`publish_catalog(gh_pages_dir, output_dir, edition_date)`:

For each `slug` in `config.SOURCES`, wrapped in the same per-source try/except isolation `main.py` uses elsewhere (one source's feed choking doesn't block the rest, and doesn't touch that source's already-published `feed.xml` if it fails):

1. Import `jugantor_epub.sources.{slug}` for `SOURCE_NAME`.
2. List existing filenames in `gh_pages_dir/{slug}/` (empty list if the folder — or the whole `gh_pages_dir` — doesn't exist yet, e.g. first run before `gh-pages` exists).
3. If `output_dir/{slug}-{edition_date}.epub` exists (today's fresh build), add it to the candidate list.
4. `keep_latest_n(candidates, config.OPDS_RETENTION_COUNT)` → copy forward every kept file not already in `gh_pages_dir/{slug}/`; evicted files are simply not carried forward (no explicit delete call needed — see below).
5. Write `gh_pages_dir/{slug}/feed.xml`.

After the loop: write `gh_pages_dir/catalog.xml` listing every configured source (even ones whose per-source step raised above).

### 3. `main.py` (modified)

After the existing `SOURCES` build loop (independent of `config.SEND_TO_KINDLE` — these are two separate delivery paths off the same build): if `config.PUBLISH_OPDS`, call `opds_publish.publish_catalog(gh_pages_dir, config.OUTPUT_DIR, edition_date)`. `gh_pages_dir` comes from wherever the workflow checked out the `gh-pages` branch (passed via an env var the workflow sets; unset/local runs skip this entirely since `PUBLISH_OPDS` defaults off).

### 4. `jugantor_epub/config.py` (modified)

```python
PUBLISH_OPDS = os.environ.get("PUBLISH_OPDS", "false").lower() == "true"
OPDS_BASE_URL = "https://mehedibangladeshi.github.io/DailyNewspaperPublish/"
OPDS_RETENTION_COUNT = 7
GH_PAGES_DIR = os.environ.get("GH_PAGES_DIR", "gh-pages-checkout")
```

### 5. `.github/workflows/daily-kindle.yml` (modified)

- Add `permissions: contents: write` to the job (needed to push `gh-pages`).
- Add a step checking out the `gh-pages` branch into `GH_PAGES_DIR`, with `continue-on-error: true` — the branch won't exist on the very first run, and a missing/empty directory is exactly "zero existing editions" to `opds_publish.publish_catalog`, no special-casing needed.
- Run `main.py` with `PUBLISH_OPDS: 'true'` and `GH_PAGES_DIR` set, alongside the existing `SEND_TO_KINDLE` env vars.
- Publish via `peaceiris/actions-gh-pages@v3`, `publish_dir: ${{ env.GH_PAGES_DIR }}`, `keep_files: false`, `force_orphan: true`.
  - `keep_files: false` is what makes eviction free — `opds_publish.publish_catalog` already stages the exact final tree (kept files only), so a full-replace publish is all that's needed; no separate delete-from-git step.
  - `force_orphan: true` keeps `gh-pages` a single squashed commit instead of accumulating a new commit every day forever on a public repo.

## Why not the alternatives considered

- **One flat feed with `<category>` tags per source** (the prototype's original shape) — worked fine at 2 sources but was rejected once the real scale (5–7 sources × up to 7 editions ≈ up to 49 mixed entries) made a single flat list unpleasant to browse on an e-ink screen.
- **Date-wise navigation** (one root entry per day, newspapers grouped underneath) — explored, diagrammed, and rejected in favor of navigating by newspaper instead.
- **Calendar-window retention** ("last 7 days") — rejected in favor of count-based ("last 7 editions") per the user's explicit wording.
- **A separate `catalog_state.json`** — rejected; the published directory listing already is the state, and a second copy is one more thing that can drift out of sync with it.
- **Date subfolders** (`2026-08-13/jugantor.epub`) instead of per-source folders — rejected once the structure reverted to per-source; no OPDS client browses raw folders, only the generated XML matters, so there's nothing to gain from reorganizing storage away from what `epub_builder.py` already produces.

## Testing

- `tests/test_opds_catalog.py` — pure unit tests, no network, fixture-style consistent with the rest of the suite: `keep_latest_n` (exactly-7, fewer-than-7, eviction-on-8th, gaps-don't-matter), `parse_edition_filename` (valid/invalid names), `format_entry_title` (single- and double-digit days), and a well-formedness check on `render_source_feed_xml`/`render_root_feed_xml` output via stdlib `xml.etree.ElementTree.fromstring` (no Java/epubcheck dependency needed here, unlike the epub build tests).
- `opds_publish.publish_catalog` itself is not unit tested — thin I/O wrapper, same treatment as `send_to_kindle()` and `_get()` elsewhere in the codebase.

## Out of scope (YAGNI, not building now)

- Auth of any kind — public/no-auth was the explicit choice.
- Supporting OPDS on Kindle itself (no client exists in stock firmware) — email delivery remains the Kindle path, untouched by this design.
- A configurable retention count or per-source retention override — fixed at 7 for all sources; revisit only if that stops fitting.
- Full-text search / OPDS search extension — not needed at this catalog size.
